## 1. Executive Summary & Architectural Context

In the 4-person team pipeline, **Person 2** owns the descriptive and statistical representation of raw business records and candidate pairs:
1. **Preprocessing / Normalization (`src/preprocessing/`)**: Cleans raw names, addresses, and country codes into standardized, multilingual-safe representations.
2. **Corpus Statistics Mining (`src/preprocessing/corpus_stats.py`)**: Mines locale-specific legal suffixes (including French `SARL`, `SAS`, `EURL` for test distribution shift, Indian `Pvt Ltd`, and US `LLC`/`Inc`) and DBA markers without hardcoding.
3. **Pairwise Feature Engineering (`src/features/`)**: Vectorized feature construction producing the official `features.parquet` table across 36 leak-free features.

```
Raw TSVs (P4 Loaders)
       ↓
[P2 Preprocessing: preprocess_records_df] → records.parquet
       ↓
[P1 Candidate Generation] → candidates.parquet & retrieval_events.parquet
       ↓
[P2 Feature Engineering: build_features] → features.parquet
       ↓
[P3 ML Models & Decision Layer] → scores.parquet & predictions
       ↓
[P4 Pipeline Orchestrator] → matching_results.tsv & candidate_pairs.tsv
```

## 3. Data Contracts & Schemas

### A. Preprocessed Records (`records.parquet`)
Generated by `preprocess_records_df(df)`:
- `entity_id` (`string`): Unique entity ID (e.g. `"S1-12345"`).
- `source` (`string`): Entity source (`"S1"`, `"S2"`, or `"S3"`).
- `raw_name` (`string`): Original unnormalized name.
- `raw_address` (`string`): Original unnormalized address.
- `raw_country` (`string`): Original country string.
- `norm_name_cons` (`string`): Conservative normalized name (Unicode NFKC, casefolded, punctuation-stripped, accents folded).
- `norm_name_aggr` (`string`): Aggressive normalized name (stripped leading trade markers and trailing legal suffixes).
- `norm_address_cons` (`string`): Conservative normalized address.
- `country_norm` (`string`): Standardized uppercase country code.

### B. Pairwise Features (`features.parquet`)
Generated by `build_features(candidates_df, records_df, retrieval_events_df)`:

| Feature Category | Feature Column Name | Dtype | Missing / NaN Semantics | Description |
|---|---|---|---|---|
| **Key Columns** | `pair_key`<br>`s1_id`<br>`candidate_id` | `string`<br>`string`<br>`string` | None | Canonical key `s1_id + "::" + candidate_id` and string IDs. |
| **Name Features** (11 cols) | `name_exact_cons`<br>`name_exact_aggr`<br>`name_char_cos`<br>`name_token_sort_ratio`<br>`name_token_set_ratio`<br>`name_containment_s1_in_cand`<br>`name_containment_cand_in_s1`<br>`name_len_diff`<br>`name_len_ratio`<br>`name_token_count_diff`<br>`name_first_token_match` | `float32` | 0.0 if empty | Exact match flags, 3-4 char n-gram cosine, RapidFuzz token sort/set, directional token containment, token/char length diffs, first token match. |
| **Address Features** (9 cols) | `addr_exact_cons`<br>`addr_char_cos`<br>`addr_token_sort_ratio`<br>`addr_containment_s1_in_cand`<br>`addr_containment_cand_in_s1`<br>`addr_len_diff`<br>`addr_num_jaccard`<br>`addr_num_conflict`<br>`addr_first_num_match` | `float32` | **`np.nan` if address missing** | Exact address match, char cosine, token sort, directional containment, length diff, numeric token Jaccard, soft numeric conflict flag, first numeric token match. |
| **Country & Missingness** (8 cols) | `country_eq`<br>`name_missing_cand`<br>`addr_missing_s1`<br>`addr_missing_cand`<br>`addr_missing_either`<br>`min_name_addr_sim`<br>`max_name_addr_sim`<br>`both_strong_match` | `float32` | `country_eq` is `np.nan` if country missing | Country equality flag, explicit missingness flags, min/max lexical similarity interactions, strong dual match indicator. |
| **Retrieval Metadata** (8 cols) | `n_routes`<br>`retrieval_best_rank`<br>`retrieval_best_score`<br>`retrieved_by_exact_name`<br>`retrieved_by_tfidf_name`<br>`retrieved_by_tfidf_address`<br>`retrieved_by_numeric`<br>`retrieved_by_reverse` | `float32` | `np.nan` if route not hit | Count of distinct routes that found pair, minimum retrieval rank, maximum retrieval score, binary route provenance flags. |

## 5. Domain Evidence & Guardrail Verification

Person 2's implementation is verified against the challenge ground-truth evidence:

1. **Subset Match (Example 66 - Kalyani):**
   * `Kalyani` $\subset$ `Kalyani Welfare Society`: `name_containment_cand_in_s1 = 1.0`, `name_first_token_match = 1.0`.
2. **Address-Only Match (Example 69 - NEXGILD):**
   * `Oncology Associates` vs `NEXGILD`: `addr_char_cos > 0.90`, `name_char_cos < 0.20`.
3. **Blank Address (Example 71):**
   * Missing address sets `addr_missing_cand = 1.0` and preserves `NaN` for similarity metrics rather than zero-filling.
4. **Digit Typo / Corrupted Number (Example 71):**
   * `703 Beacon Court` vs `70 Beacon Court`: `addr_num_conflict = 1.0`, `addr_num_jaccard = 0.0`, `addr_char_cos > 0.70` (soft signal, not hard filter).
5. **Multilingual & Mixed-Script (Example 68 - Damani):**
   * Devanagari script (`दिल्ली`) is preserved intact using Unicode character category filters (`L*`, `M*`, `N*`).
6. **French Distribution Shift:**
   * `corpus_stats.py` dynamically mines `SARL`, `SAS`, `EURL`, `SCI`, `EI` from corpus statistics without hardcoding static English-only lists.
7. **Zero Label Leakage:**
   * Normalization and feature definitions are strictly label-free and do not reference ground-truth match files.
